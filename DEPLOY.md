# Деплой GLiDE-27B на Tesla A100 — порядок действий

Runbook переезда бенчмарка роутинга с `fastino/GLiDE-0.8B` (RTX 5070 Ti, Windows) на
`fastino/GLiDE-27B` (Tesla A100, изолированный контур). Задача та же: choice-роутинг
запросов по описаниям агентов из `desc.py` (6 классов, опционально +idp).

> API у всего семейства GLiDE одинаковый (`Glide.from_pretrained` → `decide` / `decide_batch`),
> поэтому изменения кода минимальны — см. этап 3.

---

## Этап 0. Подготовка артефактов (вне контура, с интернетом)

1. **Скачать репозиторий модели** (~52+ ГБ):
   ```bash
   hf download fastino/GLiDE-27B --local-dir GLiDE-27B
   ```
   Внутри — веса (шардированные safetensors), `decision_config.json`, `readout.safetensors`,
   токенизатор и **пакет `glide/`**. Правило: использовать `glide/` из этого репозитория,
   не смешивать с пакетом от 0.8B (форматы чекпоинтов могут отличаться).
2. **Скачать колёса зависимостей** под платформу контура (Linux + CUDA + Python 3.12):
   ```bash
   pip download -d wheels/ \
     "torch==2.14.0" "transformers==5.17.0" "tokenizers==0.23.2" "safetensors==0.8.0" \
     "huggingface_hub" "jinja2" "numpy" "pillow" \
     "flash-linear-attention==0.5.2" "causal-conv1d" \
     --platform manylinux2014_x86_64 --python-version 3.12 --only-binary=:all:
   ```
   `flash-linear-attention` и `causal-conv1d` — оптимизированные кернелы для linear-attention
   слоёв. На Windows они не ставились и инференс шёл через медленный reference-путь
   («falling back… much slower» в логе). На Linux ставятся — это главный выигрыш в скорости.
3. Проверить условия **Fastino Community License** (`LICENSE`, `NOTICE` в репозитории).

## Этап 1. Окружение в контуре

1. `python3.12 -m venv venv && source venv/bin/activate`
2. Установка офлайн: `pip install --no-index --find-links wheels/ -r requirements.txt`
   (requirements.txt взять из репозитория модели).
3. Проверка кернелов:
   ```python
   import causal_conv1d, flash_linear_attention  # оба должны импортироваться
   ```
   Если их нет — инференс заработает, но заметно медленнее.

## Этап 2. VRAM-план (проверить до старта!)

| A100 | bf16 (26B ≈ 52–54 ГБ) | Решение |
|---|---|---|
| **80 ГБ** | влезает + запас на активации | ставить целиком, `token_budget` можно поднять (дефолт 16384 padded-токенов/микробатч) |
| **40 ГБ** | **не влезает** | NVFP4-квантовая версия репо (loader читает `quantization_config: modelopt/NVFP4`) или 8-бит |

Vision-энкодер не нужен (задача текстовая) — грузить с `vision=False`, сэкономит несколько ГБ.

## Этап 3. Код

Раннер уже параметризован (`run_glide_top15.py` в ветке `deploy`):

```bash
# топ-15, 6 классов, батч 8, без vision:
python run_glide_top15.py --model /path/to/GLiDE-27B --batch 8 --top 15
# с фолбэком idp (лейбл «Нет подходящего агента…» — см. caveat ниже):
python run_glide_top15.py --model /path/to/GLiDE-27B --batch 8 --idp
```

Что изменилось относительно версии для 0.8B:
- `--model` — путь к репозиторию; `sys.path` указывает на `glide/` внутри него;
- `--vision` — по умолчанию выключен (текстовая задача);
- `--batch N` — инференс через `decide_batch` (несколько промптов ~10.8к токенов в одном
  forward; на 80 ГБ поднять `token_budget` в `from_pretrained`, вмещающий N×11к).

Не помогло и не делать: prefix-cache/переиспользование общего префикса — в промпте GLiDE
state стоит **до** блока опций, общий префикс между запросами — только chat-template.

## Этап 4. Smoke-тест

1. Один запрос:
   ```python
   from glide import Glide
   m = Glide.from_pretrained("/path/to/GLiDE-27B", device="cuda", vision=False)
   print(m.decide("взять кредит", {"agent": {"type": "choice",
        "instructions": "Какой агент ответит на запрос пользователя?",
        "criteria": {/* mapping из desc.py */}}})["answers"]["agent"]["choice"])
   # ожидаемо: Кредиты
   ```
2. `nvidia-smi` — фактическая VRAM под модель+активации.
3. Латентность на батче 1 / 8 / 32 — выбрать рабочий размер батча.

## Этап 5. Бенчмарк и сверка

1. Прогнать топ-15 (90 запросов, 6 классов) → сравнить с 0.8B: **77.8%** (top-15),
   **74.5%** (top-100, 600 запросов).
2. Файлы результатов: `results_glide_27b_top{15,100}{,_idp}.xlsx`
   (суффикс `_27b` в имени файла ставится автоматически, т.к. путь модели не `…GLiDE-0.8B`).
3. Отчёты: `make_report.py` читает xlsx по фиксированным именам — для 27B либо переименовать
   результаты, либо добавить в `MODELS` новую карточку модели.
4. Caveat **idp-фолбэка**: на 0.8B наивная опция-фолбэк («Нет подходящего агента…») —
   «магнит»: 99/105 запросов ушли в idp (точность 20% против 77.8%). Проба формулировок:
   лучший вариант — лейбл «Другое» (45.7%, ложных 51/90), но всё равно плохой. Перед
   top-100 с idp зафиксировать формулировку или перейти на порог по вероятности
   (idp как класс-опцию не использовать).

## Известные ловушки

- **Офлайн:** `HF_HUB_OFFLINE=1`, `from_pretrained(local_dir)` — без сети работает.
- **Фрагментация VRAM** при больших батчах: `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`.
- **Windows-специфика уходит**: WDDM-свопа на Linux нет; у FRIDA на 5070 Ti он давал ×3 замедление
  (847 с на 105 запросов с 7 длинными опциями). Если на A100 будет крутиться и FRIDA — поднять
  `rows_per_forward` (у нас 1 из-за 16 ГБ) и можно снизить `option_max_tokens` 8192→4096
  (точность не менялась).
- **Версии:** requirements у Fastino валидированы на torch 2.14 / transformers 5.17 / Python 3.12.
  0.8B работал и на torch 2.11 / transformers 5.23, но для 27B лучше их сет.
- **`--top 100 --idp` не запускать** без зафиксированной формулировки фолбэка (см. этап 5.4).
